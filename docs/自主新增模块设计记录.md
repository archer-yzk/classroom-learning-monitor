# 自主新增模块设计记录

## 一、基本信息

- 项目名称：课堂学情监控管理系统
- 自主模块名称：学情预警与教师跟进
- 模块提出人：学生本人
- 方案确定日期：2026-09-11
- 当前文档状态：模块开发、验收、正式说明文档和运行截图均已完成
- AI 使用说明：AI 辅助整理候选方案与技术设计，最终模块由学生本人选择为“学情预警与教师跟进”

## 二、需求背景

现有系统能够采集学生的 1～6 分课堂理解程度，并向教师展示班级整体统计结果，但整体平均分和图表不能直接告诉教师“哪些学生正处于明显困难状态”，也没有记录教师是否已经进行针对性跟进。

因此，本模块在原有学情反馈基础上增加一个闭环处理流程：当学生提交 1 分或 2 分反馈时，系统自动产生学情预警；教师查看预警后填写辅导意见并标记为已处理；学生可以查看自己的预警状态和教师意见。

该模块只扩展课堂学情监控业务，不改变 PRD 中原有反馈、统计和讨论功能的含义。

## 三、模块目标

1. 自动发现提交 1 分或 2 分反馈的学生，减少教师手工筛查数据的工作量。
2. 向教师提供清晰的待处理预警列表，显示学生、课堂、分数和发生时间。
3. 记录教师的处理意见、处理人和处理时间，形成可追溯的教学跟进记录。
4. 允许学生查看自己的预警和教师意见，形成“反馈—预警—处理—查看”的完整闭环。
5. 提供可重复、可截图、可在答辩中演示的完整前后端流程。

## 四、用户角色与权限

### 4.1 学生

- 学生提交 1 分或 2 分反馈后，由系统自动触发预警。
- 学生只能查看属于自己的预警记录。
- 学生可以查看预警状态和教师处理意见，不能修改或删除预警。

### 4.2 教师

- 教师只能查看自己所授课程产生的学情预警。
- 教师可以按“待处理、已处理”状态筛选预警。
- 教师可以为待处理预警填写处理意见并标记为已处理。
- 教师不能处理其他教师课程中的预警。

### 4.3 管理员

- 本模块暂不增加管理员操作页面。
- 管理员继续负责账号和系统参数管理，不直接参与教学预警处理。

## 五、核心业务规则

1. 预警阈值固定为反馈分数小于或等于 2 分。
2. 学生提交 3～6 分反馈时不产生预警。
3. 同一学生在同一课堂中已经存在“待处理”预警时，再次提交 1 分或 2 分，只更新这条预警的最新反馈、最新分数和更新时间，不重复创建多条待处理记录。
4. 如果原预警已经处理，学生之后再次提交 1 分或 2 分，则创建一条新的待处理预警，从而保留历史处理记录。
5. 较高分反馈不会自动关闭已有预警；预警必须由教师查看后处理，避免学生的困难记录被系统静默忽略。
6. 教师处理时必须填写 1～500 字的处理意见。
7. 处理成功后保存处理教师和处理时间，状态从 `pending` 变为 `resolved`。
8. 预警记录不提供普通用户删除功能，保证教学跟进过程可追溯。

## 六、数据流程

```text
学生提交课堂反馈
        ↓
后端保存 feedback_records
        ↓
判断分数是否为 1 或 2
   ├─ 否：结束，不创建预警
   └─ 是：查找该学生本课堂的待处理预警
            ├─ 已存在：更新最新分数和反馈
            └─ 不存在：创建 learning_alerts 记录
                         ↓
                  教师查看待处理预警
                         ↓
                  填写处理意见并确认
                         ↓
              保存处理人、时间和已处理状态
                         ↓
                  学生查看教师处理结果
```

## 七、数据库表初步设计

新建数据表：`learning_alerts`

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `id` | Integer | 是 | 预警编号，主键，自增 |
| `session_id` | Integer | 是 | 关联课堂场次 |
| `student_id` | Integer | 是 | 关联产生预警的学生 |
| `latest_feedback_id` | Integer | 是 | 关联最近一次低分反馈 |
| `latest_score` | Integer | 是 | 最近一次预警分数，只允许 1 或 2 |
| `status` | String | 是 | `pending` 待处理或 `resolved` 已处理 |
| `teacher_note` | Text | 否 | 教师处理意见，最多 500 字 |
| `handled_by` | Integer | 否 | 处理预警的教师编号 |
| `created_at` | DateTime | 是 | 首次产生时间 |
| `updated_at` | DateTime | 是 | 最近一次更新时间 |
| `resolved_at` | DateTime | 否 | 完成处理时间 |

约束与索引：

- `session_id` 关联 `course_sessions.id`。
- `student_id`、`handled_by` 关联 `users.id`。
- `latest_feedback_id` 关联 `feedback_records.id`。
- `latest_score` 只能为 1 或 2。
- `status` 只能为 `pending` 或 `resolved`。
- 为课堂、学生和状态建立索引，方便教师和学生快速查询。

## 八、后端接口初步设计

### 8.1 低分反馈触发预警

- 复用现有学生反馈提交接口。
- 反馈保存成功后调用预警服务。
- 分数大于 2 时不进行额外写入。

### 8.2 学生查询自己的预警

- 请求方式：`GET`
- 地址：`/api/student/learning-alerts`
- 权限：仅学生
- 返回：当前学生的预警状态、课堂信息、分数、教师意见和相关时间。

### 8.3 教师查询课程预警

- 请求方式：`GET`
- 地址：`/api/teacher/learning-alerts`
- 可选条件：`status=pending` 或 `status=resolved`
- 权限：仅教师，只返回本人所授课程。

### 8.4 教师处理预警

- 请求方式：`PATCH`
- 地址：`/api/teacher/learning-alerts/{alert_id}`
- 提交内容：教师处理意见。
- 权限：仅负责该课程的教师。
- 结果：状态改为已处理，同时保存处理教师和处理时间。

- 课程和课堂主题

- 待处理或已处理状态

### 9.2 教师页面

新增“学情预警与跟进”区域，显示：

- 待处理预警数量

- 处理意见输入框和“完成处理”按钮

当前时段的待处理预警优先显示，已经处理的记录可切换查看。

## 十、异常情况与权限保护

1. 未登录用户访问预警接口，返回 401。
2. 学生访问教师处理接口，返回 403。
3. 教师处理其他教师课程的预警，返回 403 或 404。
4. 处理不存在的预警，返回 404。
5. 处理意见为空或超过 500 字，返回 422。
6. 重复处理已完成的预警时返回明确提示，不重复覆盖历史处理结果。
7. 被停用账号不能查看或处理预警。

## 十一、验收演示流程

1. 学生 `student001` 登录并提交 2 分反馈。
2. 教师 `teacher001` 登录，在预警区域看到张三的待处理预警。
3. 学生再次提交 1 分，教师刷新后看到同一条待处理预警更新为 1 分，而不是出现重复待处理记录。
4. 教师填写“课后复习 FastAPI 路由，并在讨论区提出不懂的问题”并完成处理。
5. 预警状态变为已处理，并显示处理教师和处理时间。
6. 学生重新登录，在“我的学情提醒”中看到教师处理意见。
7. 学生再次提交低分，系统创建新一轮待处理预警，旧的处理历史仍保留。

## 十二、不在本模块范围内的内容

- 不使用机器学习预测学生成绩。
- 不增加复杂的预警阈值配置页面。
- 不增加批量删除预警功能。
- 不修改原有 1～6 分反馈含义和统计方式。
